# 第二阶段 Task SFT 方案

本文档定义 `typst coder` 项目的第二阶段训练方向。第一阶段 completed pretraining 的目标是让模型先学会 Typst 分布；第二阶段 task SFT 的目标则是把这种领域能力转化为可用的任务能力。

当前阶段只讨论如何基于现有 Typst 语料自动构造 SFT 样本，不讨论 RL，也不优先依赖外部 instruction 数据集。

## 1. 第二阶段的目标

第二阶段的核心目标不是继续提升纯语言模型 loss，而是让模型开始学会执行明确任务，例如：

- 补全 Typst 文件
- 在已有 Typst 文档中补写缺失片段
- 根据明确要求编辑 Typst
- 修复 Typst 中的合成错误

也就是说，这一阶段要解决的是“模型是否像一个可用的 Typst coder”，而不只是“模型是否更像 Typst 语言模型”。

## 2. 第一版任务范围

第一版 task SFT 只做以下四类任务：

1. 续写 / 补全
2. 中间补全
3. 结构化编辑
4. 报错修复

这四类任务都可以较稳定地从现有 `typst-only` 语料自动构造出来，不依赖大规模人工标注，也不需要一开始就引入复杂的自然语言监督。

## 3. 为什么暂不优先做自然语言到完整 Typst

虽然“根据自然语言需求生成完整 Typst 文档”是最终很重要的能力，但第一版不应将其作为主任务，原因如下：

- 当前语料天然不包含高质量 instruction-response 配对
- 如果硬从原始仓库语料中反推自然语言需求，容易构造出质量不稳定的监督信号
- 对小模型来说，先学会补全、编辑和修复，通常比一开始追求完整文档生成更稳

因此，第一版 task SFT 应优先围绕“Typst 文件操作任务”展开。

## 4. 任务一：续写 / 补全

### 4.1 任务目标

让模型学会根据 Typst 文件前文续写后文。

### 4.2 输入输出形式

- 输入：Typst 文件的前半段
- 输出：该文件的后半段

### 4.3 构造方式

从现有 Typst 文件中，按长度和结构选取一个切分点：

- 将切分点之前的内容作为输入
- 将切分点之后的内容作为输出

切分点不应总是固定在正中间，而应在合理范围内随机变化，以避免任务过于单一。

### 4.4 任务价值

- 构造最简单
- 数据量最稳定
- 最接近代码模型天然擅长的行为
- 可作为第二阶段的主任务

### 4.5 第一版优先级

- 最高优先级

## 5. 任务二：中间补全

### 5.1 任务目标

让模型学会根据上下文补写 Typst 文件中间缺失的一段内容。

### 5.2 输入输出形式

- 输入：删去中间某一段后的 Typst 文件上下文
- 输出：被删除的中间片段

### 5.3 构造方式

从完整 Typst 文件中：

- 选择一个中间片段作为待补全区域
- 保留该片段前后的上下文
- 将被挖掉的片段作为目标输出

待补全区域应避免过短，也应避免总是落在相同结构位置。

### 5.4 任务价值

- 比单纯续写更接近真实编辑场景
- 可以让模型更早学会局部条件生成
- 对未来做文件级编辑有直接帮助

### 5.5 第一版优先级

- 第二优先级

## 6. 任务三：结构化编辑

### 6.1 任务目标

让模型学会根据明确编辑要求，对现有 Typst 文档进行定向修改。

### 6.2 输入输出形式

- 输入：原始 Typst 文档 + 编辑指令
- 输出：编辑后的 Typst 文档

### 6.3 构造方式

第一版建议使用规则化编辑任务，而不是依赖复杂自然语言指令生成。

可优先构造以下类型：

- 修改标题文本
- 插入一个标题或小节
- 向列表中新增一项
- 将一段文本替换为另一段文本
- 插入一个表格、公式块或引用块
- 调整已有结构的局部内容

编辑指令应尽量明确、低歧义，并且编辑前后结果应能自动验证。

### 6.4 任务价值

- 是从“补全模型”走向“可编辑模型”的关键一步
- 可以逐步引入任务化控制能力
- 与未来真实用户需求较接近

### 6.5 第一版优先级

- 第三优先级

## 7. 任务四：报错修复

### 7.1 任务目标

让模型学会将损坏的 Typst 代码修复回可用版本。

### 7.2 输入输出形式

- 输入：带错误的 Typst 代码 + 修复要求
- 输出：修复后的正确 Typst 代码

### 7.3 构造方式

第一版不要求真实用户报错分布，可以从正确 Typst 文件中自动合成错误样本，例如：

- 删除必要的闭合结构
- 打乱括号或分隔符
- 破坏宏参数结构
- 删除 import 或 include 的关键部分
- 对局部 block 结构做可控破坏

目标输出始终使用原始正确文件或正确片段。

### 7.4 任务价值

- 适合结合 Typst 编译器做自动验证
- 很适合后续 verifier 和 preference 学习
- 是高价值但构造要谨慎的一类任务

### 7.5 第一版优先级

- 第四优先级

## 8. 第一版任务优先级排序

第一版建议按以下优先级构造和训练：

1. 续写 / 补全
2. 中间补全
3. 结构化编辑
4. 报错修复

如果工程时间有限，建议先只做前两类任务，先建立一个可靠的 task SFT baseline，再逐步加入编辑和修复任务。

## 9. 第一版暂不做的任务

为避免目标过多，第一版暂不优先做以下内容：

- 大规模自然语言到完整 Typst 文档生成
- 多轮对话式 Typst 编辑
- 偏好优化
- RL
- 依赖复杂人工标注的高成本 instruction 数据

## 10. 第二阶段与第一阶段的关系

第一阶段 continued pretraining 解决的是：

- 模型是否真正学到了 Typst 语言分布

第二阶段 task SFT 解决的是：

- 模型是否能把 Typst 知识转化为具体任务能力

因此，第二阶段的训练样本构造应建立在第一阶段已经完成的 `typst-only` 基础上，而不应完全跳过 continued pretraining 直接做 task SFT。

## 11. 后续扩展方向

如果第一版 task SFT 有效，后续可以逐步扩展到：

- 更强的编辑任务
- 更接近真实用户错误的修复任务
- 少量高质量自然语言到 Typst 生成
- verifier 驱动的数据过滤
- preference 学习和 RL

## 12. 续写 / 中间补全的第一版采样规则

第一版 task SFT 应优先把 `续写 / 补全` 和 `中间补全` 做成稳定、低噪声、可批量构造的样本。当前阶段不追求复杂构造策略，优先保证样本质量和任务定义清晰。

### 12.1 采样语料范围

- 只从清洗后的 `typst-only` 语料中采样
- 不从 Markdown 或其他辅助文本中构造这两类任务
- 不优先使用噪声较高的测试碎片、边界样例和最小复现样本

### 12.2 文件长度要求

只有长度足够的 Typst 文件才用于构造续写和中间补全任务。

原因是：

- 太短的文件无法形成有意义的上下文
- 太短的目标片段监督价值很低
- 过短样本容易让任务退化成记忆碎片而不是学习结构

因此，第一版应额外设置用于 task SFT 的最小长度门槛，并保证输入和输出都具有足够信息量。

### 12.3 切分位置原则

切分位置应具备一定随机性，但不能完全无约束。

应避免以下情况：

- 切分点总是固定在文档正中间
- 切分点过于靠前，导致模型几乎需要生成整篇文档
- 切分点过于靠后，导致目标输出只剩很短一段

更合理的做法是：

- 在一个相对稳定的中间区域随机选取切分点
- 尽量避免落在文档极端位置

### 12.4 结构边界优先

第一版应优先在结构边界附近切分，而不是只按纯随机字符或 token 切分。

优先考虑的边界包括：

- 标题边界
- 段落边界
- 列表块边界
- 表格块边界
- 数学块或引用块边界

这样做的好处是：

- 输入更自然
- 输出更完整
- 任务更接近真实文档操作场景

### 12.5 目标片段长度控制

无论是续写还是中间补全，目标片段都应控制在“足够长但不过分长”的范围内。

第一版的原则应是：

- 不保留极短目标片段
- 不让目标片段长到接近整篇文档
- 尽量让目标片段包含完整结构，而不是只包含零散 token

## 13. 任务一：续写 / 补全的采样细则

### 13.1 输入输出定义

- 输入：文档前文
- 输出：文档后文

### 13.2 构造原则

从符合长度要求的 Typst 文件中：

- 选择一个位于合理区间内的切分点
- 将切分点前的内容作为输入
- 将切分点后的内容作为输出

### 13.3 第一版建议

- 续写任务应作为第二阶段的主任务
- 优先保证样本稳定和规模充足
- 切分点尽量落在结构边界附近

### 13.4 任务价值

续写任务最适合做第二阶段基线，原因是：

- 构造最直接
- 噪声最低
- 与 continued pretraining 的衔接最自然
- 能较快提升 Typst 文件延续能力

## 14. 任务二：中间补全的采样细则

### 14.1 输入输出定义

- 输入：文档前文 + 文档后文
- 输出：中间缺失片段

### 14.2 构造原则

从符合长度要求的 Typst 文件中：

- 选择一个位于中间区域的片段作为待补全区域
- 保留该片段之前和之后的上下文
- 将被删除的片段作为目标输出

### 14.3 第一版建议

- 缺失区域不应过短
- 缺失区域尽量对应完整结构或完整局部块
- 前后文都应保留足够上下文，避免任务退化成仅靠一侧猜测

### 14.4 任务价值

中间补全比续写更接近真实编辑使用场景，适合作为第二阶段的次主任务。

它的主要价值在于：

- 让模型学会利用双侧上下文
- 提前培养局部编辑能力
- 为后续结构化编辑任务打基础

## 15. 第一版建议任务配比

如果第一版只围绕 `续写 / 中间补全` 做 SFT 基线，建议优先采用偏向续写的配比：

- `续写 / 补全`：主任务
- `中间补全`：次任务

这样做的原因是：

- 续写更稳定
- 续写更容易保证样本质量
- 中间补全虽然重要，但构造噪声和边界处理复杂度更高

第一版不建议让中间补全占比超过续写任务。

## 16. 任务三：结构化编辑的采样细则

第一版结构化编辑任务应优先采用规则清晰、可自动验证、低歧义的编辑类型，而不是复杂开放式指令。

### 16.1 输入输出定义

- 输入：原始 Typst 文档 + 明确编辑指令
- 输出：编辑后的 Typst 文档

### 16.2 构造原则

第一版应从完整 Typst 文件出发，通过规则化变换自动构造“编辑前 / 编辑后”样本。

也就是说：

- 先选取一个原始正确文档
- 对其中某个局部结构施加明确变换
- 将变换前文档作为输入上下文
- 将变换后的文档作为目标输出

### 16.3 第一版优先支持的编辑类型

建议优先支持以下低歧义编辑任务：

- 修改标题文本
- 插入一个标题或小节
- 向已有列表中新增一项
- 将某段文本替换为另一段文本
- 在现有结构中插入一个简单表格
- 在现有结构中插入一个公式块、引用块或代码块

这些编辑类型的共同特点是：

- 可通过规则自动构造
- 编辑意图清晰
- 编辑结果容易检查

### 16.4 第一版暂不优先支持的编辑类型

为避免样本质量失控，第一版暂不优先做以下编辑：

- 高层次开放式重写
- 多处联动的大规模结构改写
- 风格迁移类编辑
- 需要深层语义理解才能完成的复杂编辑

### 16.5 样本质量要求

第一版结构化编辑样本应满足：

- 编辑指令明确且单一
- 编辑前后差异局部、可追踪
- 目标文档保持 Typst 结构正确
- 尽量避免一次样本中叠加多个无关编辑动作

### 16.6 任务价值

结构化编辑任务的主要价值在于：

- 让模型开始学习“按要求修改已有 Typst”
- 为未来真实用户编辑场景打基础
- 帮助模型从“补全”过渡到“受控生成”

## 17. 任务四：报错修复的采样细则

第一版报错修复任务应以“从正确文件自动注入错误”为主，而不是直接追求真实用户错误分布。

### 17.1 输入输出定义

- 输入：带错误的 Typst 代码 + 修复要求
- 输出：修复后的正确 Typst 代码

### 17.2 构造原则

从正确的 Typst 文件或正确片段出发：

- 对其中一处局部结构施加可控破坏
- 将破坏后的内容作为输入
- 将原始正确内容作为输出

第一版不追求错误多样性最大化，而应优先保证：

- 错误是可解释的
- 修复目标是唯一或近似唯一的
- 样本可验证

### 17.3 第一版优先注入的错误类型

建议优先从以下可控错误开始：

- 删除必要的闭合结构
- 打乱括号、分隔符或局部 block 结构
- 破坏宏参数形式
- 删除 import 或 include 的关键部分
- 在表格、列表、数学块中做局部结构破坏

这些错误更适合第一版，原因是：

- 自动构造容易
- 验证相对直接
- 更贴近语法或局部结构修复能力

### 17.4 第一版暂不优先支持的错误类型

第一版不建议优先构造以下高噪声修复任务：

- 需要大范围语义重写才能修复的错误
- 多处同时损坏的复杂错误
- 依赖外部资源或仓库上下文才能判断的错误
- 修复结果存在大量合理答案的模糊错误

### 17.5 样本质量要求

第一版报错修复样本应满足：

- 错误尽量局部
- 原始正确答案明确
- 修复后文档应保持 Typst 结构正确
- 单一样本中的错误类型不宜过多叠加

### 17.6 任务价值

报错修复任务的主要价值在于：

- 天然适合和 Typst 编译器结合做自动验证
- 很适合后续 verifier、ranking 和 preference 数据构造
- 对真实使用中的调试场景有直接价值

## 18. 四类任务的第一版定位

第一版 task SFT 的四类任务建议按以下定位理解：

- `续写 / 补全`：主任务，最稳定、最基础
- `中间补全`：次主任务，增强局部上下文建模
- `结构化编辑`：受控编辑能力的起点
- `报错修复`：面向调试和可验证训练的高价值补充

如果工程资源有限，建议采用逐步扩展策略：

1. 先做 `续写 / 中间补全`
2. 再加 `结构化编辑`
3. 最后加入 `报错修复`

## 19. 第一版训练配比建议

第二阶段不建议一开始就对四类任务平均混训。更稳妥的做法是先建立低噪声基线，再逐步增加更复杂任务的占比。

### 19.1 方案 A：最小可行基线

适用于：

- 先验证第二阶段 task SFT 是否有效
- 当前重点是低风险、低噪声地建立基线

推荐配比：

- `续写 / 补全`：`70%`
- `中间补全`：`30%`

特点：

- 最稳定
- 样本最容易构造
- 最适合第二阶段第一轮实验

### 19.2 方案 B：第一版完整混训

适用于：

- 已经完成基线实验
- 希望引入完整四类任务，但仍以稳定为主

推荐配比：

- `续写 / 补全`：`55%`
- `中间补全`：`25%`
- `结构化编辑`：`15%`
- `报错修复`：`5%`

特点：

- 仍然以补全类任务为主体
- 开始引入编辑能力
- 仅少量加入修复任务，避免高噪声影响整体训练

### 19.3 当前默认建议

当前默认建议是：

1. 先采用 `方案 A`
2. 确认第二阶段基线有效后，再升级到 `方案 B`

第一版不建议直接采用四类任务接近平均的混训方式。

## 20. 第二阶段评测方式

第二阶段评测不应只看一个总分，而应按任务类型分别评估。

原因是：

- 四类任务的目标不同
- 不同指标之间很难直接比较
- 如果只看一个混合总分，很难判断模型到底在哪类任务上真正提升

因此，第二阶段应采用“分任务评测面板”。

## 21. 各任务的建议评测指标

### 21.1 续写 / 中间补全

建议评测：

- loss
- 目标片段匹配情况
- `compile pass rate`
- 少量人工抽样检查

其中：

- `compile pass rate` 是最重要的可执行性指标
- loss 可作为辅助参考
- 人工抽样用于检查输出是否自然、是否出现明显结构问题

### 21.2 结构化编辑

建议评测：

- 编辑指令命中率
- 非目标区域保真度
- 编辑后 `compile pass rate`

这里最重要的是两件事：

- 该修改的地方是否正确修改
- 不该修改的地方是否保持稳定

### 21.3 报错修复

建议评测：

- 修复后 `compile pass rate`
- 修复成功率
- 最小改动率

其中：

- 修复成功率用于判断错误是否真正被修复
- 最小改动率用于防止模型把局部修复任务变成大规模重写

## 22. 第二阶段评测集组织方式

第二阶段建议至少保留两层任务评测集：

- `dev_task`
- `test_task`

作用分别为：

- `dev_task`：用于第二阶段调参与 checkpoint 选择
- `test_task`：用于最终结果汇报，不参与调参

如果条件允许，第二阶段的任务评测集也应尽量遵守 `repo-level` 隔离原则，避免与训练仓库高度重叠。

## 23. 当前推荐的简化评测面板

如果第二阶段第一轮不希望评测体系过于复杂，建议先采用如下最小面板：

- 主指标：`compile pass rate`
- 次指标：任务成功率
- 辅助检查：人工抽样

并且：

- 不强行合成单一总分
- 优先看分任务结果
- 先确认基线是否有效，再逐步扩展评测复杂度

## 24. compile pass rate 的定义原则

`compile pass rate` 是第二阶段最重要的可执行性指标之一，但前提是评测口径必须固定。否则，这个指标很容易混入环境噪声，导致结果不可比。

第二阶段应明确区分：

- 由模型生成问题导致的失败
- 由编译环境不完整导致的失败
- 由样本本身不适合稳定编译导致的失败

只有先区分这三类情况，`compile pass rate` 才能真正反映模型能力。

## 25. 编译失败的三类来源

### 25.1 模型导致的失败

以下情况应明确归为模型失败：

- Typst 语法错误
- 局部结构损坏
- 宏调用形式明显错误
- 编辑后文档结构不一致
- 修复任务中引入新的错误

这类失败应直接计入 `compile pass rate` 的失败样本。

### 25.2 环境导致的失败

以下情况应归为环境问题，而不是直接归因于模型：

- 缺少字体
- 缺少 package
- 缺少外部资源文件
- 图片、数据文件或引用路径不存在
- 编译环境与样本依赖环境不一致

如果不单独识别这类问题，评测结果会混淆“模型能力”和“评测环境是否完整”。

### 25.3 样本本身不适合稳定编译

以下样本不适合作为严格 compile-based 评测样本：

- 强依赖完整仓库结构才能编译
- 依赖私有资源或不可获得资源
- 原始样本本身就无法在统一环境下稳定编译
- 缺少必要上下文，无法单文件独立编译

这类样本可以保留在完整任务集中，但不应进入严格编译评测集。

## 26. 两层评测集设计

为降低 compile 评测中的环境噪声，第二阶段建议采用两层评测集。

### 26.1 strict compile set

定义：

- 只保留在统一环境下可稳定编译的样本
- 样本依赖可控
- 原始参考答案可验证

用途：

- 作为 `compile pass rate` 的主评测集合
- 用于比较不同模型或不同 checkpoint 的可执行性差异

### 26.2 full task set

定义：

- 保留更完整、更接近真实任务分布的样本
- 可包含部分依赖复杂环境或上下文的样本

用途：

- 用于观察更接近真实场景的整体表现
- compile 结果可记录，但不应作为唯一判断依据

## 27. 当前推荐的 compile 评测口径

当前推荐做法是：

- 以 `strict compile set` 上的 `compile pass rate` 作为主指标
- 在 `full task set` 上记录 compile 结果作为辅助参考
- 明确区分“模型失败”和“环境失败”

也就是说，第二阶段默认不应把所有无法编译的情况都简单记为模型失败。

### 27.1 当前已确定的评测口径

当前项目已经明确以下规则：

- package 允许自由使用
- 评测环境允许安装所需 package
- 因缺少 package 导致的失败不视为模型失败
- 因缺少字体导致的失败不视为模型失败
- 依赖外部资源的样本不进入 `strict compile set`

这意味着：

- package 缺失属于环境问题
- 字体缺失属于环境问题
- `strict compile set` 应尽量由资源依赖最少、环境依赖可控的样本组成

### 27.2 strict compile set 的排除原则

以下样本默认不进入 `strict compile set`：

- 依赖外部图片的样本
- 依赖外部数据文件的样本
- 依赖 bibliography 文件或其他外部引用文件的样本
- 依赖仓库内其他本地子文件的样本
- 依赖仓库外部资源才能稳定编译的样本

这类样本可以保留在 `full task set` 中，用于更接近真实场景的辅助评测。

这里的“依赖仓库内其他本地子文件”包括但不限于：

- 通过 `include` 引入本地文件
- 通过 `import` 引入本地模块
- 依赖多文件拼接后才能完整编译的文档

也就是说，`strict compile set` 应优先保留“单文件、资源依赖可控、在统一环境下可独立稳定编译”的样本。

## 28. 当前建议的评测原则

第一轮第二阶段实验中，建议遵循以下口径：

1. 主 compile 指标只在 `strict compile set` 上统计
2. `strict compile set` 中的失败默认视为模型失败
3. `full task set` 中的失败需额外区分模型问题和环境问题
4. 原始样本本身不可稳定编译的，不纳入严格 compile 指标

这样做的目的是让 `compile pass rate` 成为一个可比、可解释、可复现的指标，而不是一个被环境条件放大噪声的数字。

## 29. 第二阶段统一样本模板

第二阶段 task SFT 不应为每类任务单独设计完全不同的数据格式。更合理的做法是采用统一模板，只在任务说明和输入字段上做最小差异。

这样做的主要好处是：

- 让模型更容易学会“先识别任务，再执行任务”
- 降低不同任务混训时的格式干扰
- 便于后续继续扩展新任务类型
- 便于统一数据构造和评测流程

### 29.1 统一模板原则

第二阶段所有样本建议统一包含以下部分：

- `任务类型`
- `任务说明`
- `输入内容`
- `目标输出`

也就是说，模型面对的不是互相完全不同的样本结构，而是一套一致的任务框架。

### 29.2 模板设计要求

统一模板应满足以下要求：

- 字段定义稳定
- 指令语气低歧义
- 不依赖复杂自然语言修饰
- 尽量减少无关说明文字
- 便于从现有 Typst 语料自动构造

第一版不应为了“更像聊天助手”而引入过于松散的 instruction 风格。

## 30. 四类任务的字段模板

在统一模板之下，不同任务只修改必要字段。

### 30.1 续写 / 补全

建议字段：

- `任务类型`：续写
- `任务说明`：根据给定的 Typst 前文续写后续内容
- `输入内容`：文档前文
- `目标输出`：文档后文

### 30.2 中间补全

建议字段：

- `任务类型`：中间补全
- `任务说明`：根据前后文补全缺失的 Typst 片段
- `输入内容`：前文 + 后文
- `目标输出`：中间缺失片段

### 30.3 结构化编辑

建议字段：

- `任务类型`：结构化编辑
- `任务说明`：根据明确编辑要求修改 Typst 文档
- `输入内容`：原始文档 + 编辑要求
- `目标输出`：编辑后的文档

### 30.4 报错修复

建议字段：

- `任务类型`：报错修复
- `任务说明`：修复给定 Typst 代码中的错误
- `输入内容`：错误文档 + 修复要求
- `目标输出`：修复后的正确文档

## 31. 第一版模板风格建议

第一版模板风格应尽量简单、统一、机械。

建议原则如下：

- 不追求花哨 instruction
- 不大量加入礼貌性语言
- 不为每个样本构造风格各异的自然语言描述
- 优先保证任务定义一致和输出边界清晰

第二阶段第一版的核心目标不是“让样本看起来像真实对话”，而是“让模型稳定学习任务映射关系”。

## 32. 统一模板的作用边界

统一模板主要用于：

- 第二阶段 task SFT 的主训练样本
- 多任务混训时保持格式稳定
- 为后续评测和错误分析提供统一输入结构

如果未来要引入高质量自然语言到 Typst 生成数据，可以在后续阶段增加更自由的 instruction 风格，但不建议在第二阶段第一版就打破统一模板。

## 33. 第二阶段默认采用片段输出

第二阶段第一版默认采用“片段输出”策略，而不是让模型直接输出整篇编辑后文档。

这里的“片段输出”指的是：

- 模型只生成目标修改片段
- 原始上下文由外部系统保留
- 最终完整文档由外部系统将生成片段回填到对应位置

第一版采用这一策略的主要原因是：

- 更符合局部编辑和局部修复的真实目标
- 更适合小模型训练
- 更容易控制保真度
- 更容易做自动评测
- 更有利于减少“看似完成任务、实则整篇重写”的噪声

## 34. 四类任务在片段输出下的对应形式

### 34.1 续写 / 补全

- 输出目标段，而不是完整文档

### 34.2 中间补全

- 输出缺失段，而不是拼接后的完整文档

### 34.3 结构化编辑

- 输出被编辑片段，而不是整篇编辑后文档

### 34.4 报错修复

- 输出被修复片段，而不是整篇修复后文档

也就是说，第二阶段四类任务在第一版中统一遵循：

- 输入提供必要上下文
- 输出只生成目标片段

## 35. 采用片段输出的收益

第一版采用片段输出，主要有以下收益：

- 让四类任务的训练目标更加一致
- 降低小模型的生成负担
- 更容易检查局部修改是否正确
- 更容易判断非目标区域是否被错误改动
- 更便于未来在实际系统中做局部回填

## 36. 片段输出的代价与边界

采用片段输出也存在明确代价：

- 模型不会在第二阶段直接学习“输出完整最终文档”
- 需要外部系统负责片段回填
- 对整篇文档的端到端生成能力提升有限

但对于第二阶段第一版而言，这些代价是可以接受的。当前优先级应是：

- 先把局部任务做稳
- 再考虑是否扩展到整篇输出

因此，第二阶段第一版不建议以整篇重写作为默认目标形式。
