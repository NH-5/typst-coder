# 第一阶段 Continued Pretraining 方案

本文档定义 `typst coder` 项目的第一阶段训练目标与实施范围。当前阶段只做标准 `next-token` continued pretraining，不做 instruction tuning，不做 preference learning，也不做 RL。

## 1. 当前阶段的目标

第一阶段的目标不是让模型直接变成一个“按自然语言要求写完整 Typst 文档”的助手，而是先让模型具备稳定的 Typst 领域建模能力。

这一阶段只追求以下三件事：

- 更好地学习 Typst 语法与常见结构
- 更好地学习模板、宏、package 用法和文档组织方式
- 在 Typst 分布上的语言模型损失明显下降

## 2. 当前阶段不做什么

为了避免目标混乱，第一阶段明确不做以下内容：

- 不做 instruction tuning
- 不做自然语言到 Typst 的任务对齐
- 不做偏好优化
- 不做 RL
- 不把“复杂任务可用性”作为这一阶段的核心目标

如果第一阶段有效，后续再进入 task SFT。

## 3. 模型与训练目标

### 3.1 基础模型

- 使用 `Qwen3.5-0.8B-Base` 作为起点

选择 `Base` 模型的原因是它更适合继续训练，而不是在已经对话对齐过的模型上叠加领域语料。

### 3.2 训练目标

- 仅使用标准的自回归 `next-token prediction`

当前阶段不加入 fill-in-the-middle，也不加入其他额外训练目标。第一版优先保证训练路线足够简单、结果足够可解释。

## 4. 训练数据

### 4.1 语料来源

- 训练集来源：`TechxGenus/Typst-Train`
- 测试集来源：`TechxGenus/Typst-Test`

### 4.2 清洗策略

第一阶段训练语料使用已经定义好的 `typst-only` 清洗结果：

- 只保留 `language == typst`
- 进行最小长度过滤
- 进行 Typst 信号过滤
- 进行多层去重
- 对测试/边界样例降采样或降权
- 对超长样本做过滤
- 对单个 repo 施加上限，避免数据分布失衡

具体规则见：

- [data-cleaning.md](/Users/wuzheng/projects/typst-coder/docs/data-cleaning.md)

## 5. 数据划分原则

第一阶段不应只依赖官方 `Typst-Test` 作为验证依据。原因是现有公开训练集和测试集可能存在较强的来源分布重叠，因此单看官方测试集容易得到偏乐观的结论。

建议至少使用两套验证数据：

### 5.0 划分单位

- 数据划分单位是 `repo`，不是文件。
- 不允许同一个 `repo` 同时出现在训练集和内部验证/测试集中。

这样做的目的是避免模型仅仅记住某些仓库的局部风格，从而高估 continued pretraining 的泛化效果。

### 5.1 官方测试集

- 使用 `TechxGenus/Typst-Test`
- 作用：作为同分布参考指标
- 不参与训练过程中的选模
- 不参与 checkpoint 选择

### 5.2 内部 repo-level 验证集

- 从训练来源仓库中额外切出一份内部验证集
- 划分原则应尽量按 `repo` 隔离，而不是只按文件随机切分

这样做的目的是更真实地评估模型是否学到了跨项目的 Typst 模式，而不只是记住同一批仓库的局部风格。

### 5.3 推荐划分比例

第一版建议按 `repo` 采用以下默认比例：

- `train_repo`: `85%`
- `dev_repo`: `10%`
- `test_repo`: `5%`

其中：

- `dev_repo` 用于训练过程中的 checkpoint 评估和最终 checkpoint 选择
- `test_repo` 用于最终内部评估
- `Typst-Test` 作为额外公开 benchmark 单独保留

### 5.4 平衡原则

划分时优先按总字符数或近似 token 数做平衡，而不是只按文件数量平衡。

原因是不同仓库之间的文件大小分布可能差异很大：

- 有些仓库文件很少但每个文件很长
- 有些仓库文件很多但大多很短

如果只按文件数切分，容易导致各个 split 的真实语料规模明显失衡。

### 5.5 推荐使用方式

第一阶段训练中，建议按以下方式使用不同数据集：

- `train_repo`：用于 continued pretraining
- `dev_repo`：主要验证集，用于调参与 checkpoint 评估
- `test_repo`：最终内部测试集，不参与调参
- `Typst-Test`：外部辅助 benchmark，不参与选模

第一阶段最重要的验证信号应来自 `dev_repo`，而不是 `Typst-Test`。

## 6. 样本组织方式

第一阶段样本组织应优先保证实现简单、训练稳定、token 利用率高。

建议原则如下：

- 以文件内容作为原始样本单位
- 使用 packing，以提高 token 利用率
- 保留明确的文档边界信息，避免不同文件无分隔地混在一起
- 对超长文件按固定长度切分为多个 chunk

这一阶段不需要刻意追求文件级完整建模，也不需要为后续编辑任务提前加入复杂样本结构。目标只是稳定地学习 Typst 分布。

### 6.1 packing

第一阶段建议启用 packing。

这里的 packing 指的是：

- 当单个 Typst 文件长度不足一个训练序列时
- 将多个较短文件拼接到同一个固定长度序列中
- 尽量提高每个训练样本中的有效 token 占比

启用 packing 的主要原因是：

- Typst 文件中可能存在大量中短样本
- 不做 packing 会浪费大量训练长度
- continued pretraining 更关心有效 token 覆盖率，而不是单文件独占一个训练样本

因此，第一阶段默认使用 packing。

### 6.2 样本边界

第一阶段建议保留显式样本边界。

这里的样本边界指的是：

- 当多个文件被拼接到同一个训练序列中时
- 显式告诉模型某个文件已经结束，另一个文件即将开始

保留边界的主要原因是：

- 避免模型把两个本来独立的 Typst 文件误当作一个连续文档
- 降低跨文档拼接造成的分布噪声
- 在提高 token 利用率的同时，尽量保留真实文档结构感

因此，第一阶段默认策略是：

- 使用 packing
- 同时保留显式边界

也就是说，第一阶段不是“多个文件无分隔硬拼接”，而是“带边界地拼接多个文件”。

### 6.3 超长文件切分

对于超过单个训练序列长度的 Typst 文件，第一阶段按固定长度切分为多个 chunk。

这样做的目的不是精确保留整篇文档结构，而是：

- 让训练实现保持简单
- 保证长文件也能被有效利用
- 避免为了保留完整文档而牺牲训练稳定性和 token 利用率

第一阶段对长文件的处理应遵循“先简单、先稳定”的原则。

## 7. 序列长度原则

第一阶段序列长度的选择原则是：

- 优先保证训练稳定
- 优先保证显存和 batch 配置可行
- 不以“尽可能长上下文”为第一目标

对 `0.8B` 模型来说，第一轮实验应优先验证 continued pretraining 是否有效，而不是优先追求长上下文能力。

因此，序列长度应服从“先跑通、再优化”的原则。

## 8. 训练预算与 checkpoint 策略

第一阶段不使用 early stopping。

训练策略采用：

- 固定训练预算
- 固定间隔保存 checkpoint
- 在 `dev_repo` 上评估各个 checkpoint
- 训练跑满后，从所有 checkpoint 中选择表现最好的一个

这意味着：

- 训练不会因为验证集指标波动而提前停止
- 但训练过程中的 checkpoint 仍然需要系统评估
- 最终用于后续阶段或对比实验的模型，不一定是最后一个 checkpoint，而应优先选择 `dev_repo` 表现最好的 checkpoint

如果后续为了对照实验需要，也可以同时保留：

- `final checkpoint`
- `best checkpoint`

这样可以更清楚地区分“固定预算训练结果”和“本轮最佳可用结果”。

### 8.1 checkpoint 选择规则

为避免选模标准在实验过程中漂移，第一阶段应使用固定的 checkpoint 选择顺序：

1. 主指标：`dev_repo loss`
2. 次指标：`Typst-Test loss`
3. 最后参考：少量人工定性检查

具体原则如下：

- 默认情况下，只按 `dev_repo loss` 选择最佳 checkpoint
- 只有当多个 checkpoint 的 `dev_repo loss` 非常接近时，才参考 `Typst-Test loss`
- 如果数值表现仍然接近，再通过少量人工续写样例做最终判断

人工检查只用于发现明显异常，例如：

- loss 下降但输出风格明显恶化
- 语法错误显著增多
- 生成内容出现明显重复、发散或无意义结构

人工检查不是第一阶段的主排序依据。

### 8.2 训练预算表示方式

第一阶段建议优先使用 `token budget` 或 `corpus pass` 来表达训练预算，而不是只用 epoch。

推荐原因：

- continued pretraining 更适合用“模型实际看了多少 token”来描述训练强度
- 在不同切分、不同 packing 策略下，epoch 的可比性较弱
- 对当前这种窄领域语料，使用 `corpus pass` 更容易理解和执行

因此，第一阶段可以将预算表达为：

- `总训练预算 = 清洗后训练语料总 token 数 × pass 数`

如果暂时没有精确 token 统计，也可以先用近似字符数或样本长度统计辅助估算。

### 8.3 第一轮建议训练预算

第一阶段的目标是先验证 continued pretraining 是否有效，而不是一开始就追求最大训练强度。

建议分三档理解：

- 试跑版：`0.5` 个 corpus pass  
  用于检查数据流程、loss 曲线和训练稳定性。

- 正式第一轮：`2` 到 `3` 个 corpus pass  
  这是第一轮实验的推荐默认范围。

- 扩展观察轮：`5` 个 corpus pass  
  仅在 `dev_repo loss` 仍持续改善时考虑，不作为默认配置。

如果当前只打算先跑一个标准基线，建议直接采用：

- 第一轮固定训练 `3` 个 corpus pass

### 8.4 checkpoint 保存与评估频率

在固定预算训练策略下，checkpoint 不需要过密，但也不能过稀，否则无法判断训练过程中的性能变化。

第一阶段建议采用以下频率之一：

- 每完成总训练预算的 `5%` 到 `10%` 时评估一次
- 或者每 `0.25` 到 `0.5` 个 corpus pass 评估一次

如果第一轮总预算设为 `3` 个 corpus pass`，则更推荐：

- 每 `0.25` 个 corpus pass 保存并评估一次 checkpoint

这样既能观察趋势，也不会带来过重的评估负担。

### 8.5 预算是否足够的判断原则

是否增加训练预算，主要看 `dev_repo loss`，而不是 `train loss`。

判断原则如下：

- 如果 `train loss` 持续下降，但 `dev_repo loss` 基本不再改善，说明当前预算已经接近足够
- 如果 `dev_repo loss` 仍稳定下降，可以在下一轮实验中考虑增加训练预算
- 如果 `Typst-Test loss` 改善明显，但 `dev_repo loss` 改善有限，应优先相信 `dev_repo`

第一阶段最重要的是确认模型是否真正提升了 repo-level 泛化能力，而不是只对同分布样本更拟合。

## 9. 评估指标

第一阶段评估不应追求复杂指标体系，先关注最直接、最可解释的信号。

建议优先关注以下指标：

### 8.1 训练损失

- 观察训练 loss 是否稳定下降

### 8.2 内部验证损失

- 重点关注内部 repo-level dev set 上的 loss

这是第一阶段最重要的泛化参考指标。

### 8.3 官方测试集损失

- 记录 `Typst-Test` 上的 loss

它可以作为辅助指标，但不能单独用于判断模型是否真正具备更强的 Typst 泛化能力。

### 8.4 少量人工补全检查

可以额外做少量定性检查，例如：

- 给定 Typst 文件前半段，让模型续写后半段
- 观察生成结果是否更像真实 Typst
- 观察语法错误和无意义结构是否减少

这一阶段暂不把复杂任务成功率作为主指标。

## 10. 第一阶段的成功标准

如果满足以下条件，可以认为第一阶段 continued pretraining 是有效的：

- 训练过程稳定，无明显退化
- 内部 repo-level 验证集 loss 明显优于基座模型
- 官方测试集 loss 同样改善
- 人工抽查表明 Typst 风格、结构和语法质量有所提升

达到以上条件后，再进入第二阶段 task SFT，更合理也更容易判断后续改进是否来自任务对齐而不是领域语言建模本身。

## 11. 下一阶段衔接

第一阶段完成后，再讨论第二阶段 task SFT。第二阶段的目标将转为：

- 根据自然语言生成 Typst
- 基于现有 Typst 文件做编辑
- 修复 Typst 编译错误
- 学习更明确的任务输入输出格式

也就是说，第一阶段先解决“模型是否像一个 Typst 模型”，第二阶段再解决“模型是否像一个可用的 Typst coder”。
